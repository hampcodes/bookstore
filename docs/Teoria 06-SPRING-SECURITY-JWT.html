¿Qué es Spring Security?

Framework de autenticación y control de acceso para aplicaciones Java. Es el estándar de facto para asegurar apps Spring.
  • Autenticación (¿quién eres?): login con usuario/contraseña, OAuth2, JWT, LDAP…
  • Autorización (¿qué puedes hacer?): roles, permisos, expresiones en endpoints.
  • Protección contra CSRF, session fixation, clickjacking, XSS.
  • Integración limpia con Spring Boot vía spring-boot-starter-security.

Fuente: spring.io/projects/spring-security

Las 4 amenazas que Spring Security mitiga

Antes de entrar en JWT, conocé contra qué nos protege el framework:

🎯 CSRF (Cross-Site Request Forgery)

Qué es: el atacante hace que un usuario logueado ejecute una acción sin querer (ej: clic en un link malicioso que dispara POST /transfer a tu banco).

Cómo: el navegador envía las cookies de sesión automáticamente con cada request, incluso desde otro sitio.

Defensa: token CSRF único por sesión que el atacante no puede adivinar. En APIs JWT lo desactivamos (no usamos cookies, el token va en header).

🪪 Session Fixation

Qué es: el atacante "fija" un session ID en la víctima antes de que se loguee. Cuando ésta se autentica, el atacante ya tiene su sesión.

Cómo: envía un link con un JSESSIONID conocido. La víctima entra y se loguea con esa sesión.

Defensa: Spring Security regenera el session ID automáticamente al hacer login. Con JWT stateless ni siquiera aplica (no hay sesión).

🖼️ Clickjacking

Qué es: el atacante mete tu sitio en un <iframe> invisible sobre su página. El usuario cree que clickea botones de la web maliciosa pero clickea los tuyos.

Ejemplo clásico: "Click para ganar un iPhone" → el clic real va al botón "Transferir 1000" de tu banco.

Defensa: header X-Frame-Options: DENY que prohíbe ser embebido. Spring Security lo agrega por defecto.

💉 XSS (Cross-Site Scripting)

Qué es: el atacante inyecta JavaScript en tu página que se ejecuta en el navegador de otros usuarios.

Cómo: guarda un comentario tipo <script>fetch('/api/...', ...)</script> y cuando otro usuario lo ve, su navegador ejecuta el script con SUS credenciales.

Defensa: escapar HTML en outputs, headers Content-Security-Policy, y guardar tokens en cookies HttpOnly (no accesibles desde JS).

⚠️ JWT en localStorage es vulnerable a XSS: cualquier script inyectado puede leerlo. Por eso algunos prefieren cookies HttpOnly. En PagoYa usamos localStorage por simplicidad académica, pero en producción real evaluá el trade-off.

  • Para JWT escribimos nuestro propio filtro que extrae el token del header Authorization: Bearer ....

JWT — anatomía del token

Tres partes en Base64URL separadas por puntos:

xxxxx.yyyyy.zzzzz
header.payload.signature

Header

{ "alg": "HS256", "typ": "JWT" }

Payload (claims)

{
  "sub": "ana@pagoya.com",
  "role": "CUSTOMER",
  "iat": 1714867200,
  "exp": 1714870800
}

La firma garantiza integridad: si alguien edita el payload, deja de ser válida.

JWT — claims importantes

ClaimSignificadoUso típico
subSubject (usuario)Email o ID del usuario
iatIssued atCuándo se emitió
expExpirationCuándo deja de ser válido
issIssuerQuién lo emitió
audAudiencePara quién
jtiJWT IDIdentificador único (para blacklists)
roleCustom claimRol del usuario
El payload NO está cifrado, sólo firmado. Nunca pongas datos sensibles ahí.

Flujo de login con JWT

1 Cliente envía POST /api/auth/login con email + password
2 Backend valida con AuthenticationManager + UserDetailsService
3 Si OK, JwtService firma un token con HS256 + secret
4 Backend responde 200 { token: "eyJhbGci..." }
5 Cliente guarda el token y lo envía en Authorization: Bearer ...

Flujo de request protegido

1 Cliente: GET /api/customers/me + Authorization: Bearer xxx.yyy.zzz
2 JwtAuthenticationFilter extrae el token
3 Valida firma y expiración con JwtService.isValid()
4 Carga el UserDetails y crea el Authentication
5 Lo coloca en SecurityContextHolder
6 El controller ejecuta y puede leer el usuario autenticado

SecurityConfig — la cadena de filtros

@Bean
public SecurityFilterChain filterChain(HttpSecurity http, JwtAuthenticationFilter jwt) throws Exception {
  http
    .csrf(csrf -> csrf.disable())
    .sessionManagement(s -> s.sessionCreationPolicy(STATELESS))
    .authorizeHttpRequests(auth -> auth
        .requestMatchers("/api/auth/**", "/v3/api-docs/**", "/swagger-ui/**").permitAll()
        .anyRequest().authenticated()
    )
    .addFilterBefore(jwt, UsernamePasswordAuthenticationFilter.class);
  return http.build();
}
@Bean
public PasswordEncoder passwordEncoder() {
  return new BCryptPasswordEncoder();
}

Qué hace cada parte

  • csrf().disable(): la API es stateless, no usa cookies de sesión.
  • STATELESS: Spring no crea HttpSession; cada request se autentica de cero con el token.
  • permitAll(): deja pasar sin autenticación los endpoints públicos (auth + Swagger).
  • anyRequest().authenticated(): todo lo demás exige token válido.
  • addFilterBefore: nuestro filtro JWT corre antes del filtro nativo de username/password.
  • BCryptPasswordEncoder: hashea con BCrypt (algoritmo lento por diseño = resistente a fuerza bruta).

JwtService — emisión y validación

public String generateToken(UserDetails user, String role) {
  return Jwts.builder()
      .subject(user.getUsername())
      .claim("role", role)
      .issuedAt(new Date())
      .expiration(new Date(System.currentTimeMillis() + expirationMs))
      .signWith(getSigningKey())
      .compact();
}

public String extractEmail(String token) {
  return Jwts.parser().verifyWith(getSigningKey()).build()
      .parseSignedClaims(token).getPayload().getSubject();
}

public boolean isValid(String token, UserDetails user) {
  String email = extractEmail(token);
  return email.equals(user.getUsername()) && !isExpired(token);
}

Qué hace cada parte

  • generateToken: arma el JWT poniendo el email como sub, el rol como claim custom, fechas de emisión y expiración, y lo firma con la llave secreta.
  • signWith: aplica HMAC-SHA256 con el secret. Garantiza que nadie pueda alterar el token sin invalidar la firma.
  • extractEmail: parsea el token, verifica la firma y devuelve el subject. Si la firma es inválida, lanza excepción.
  • isValid: dos condiciones: el email del token coincide con el usuario cargado, y no está expirado.

JwtAuthenticationFilter

String header = request.getHeader("Authorization");
if (header == null || !header.startsWith("Bearer ")) {
    filterChain.doFilter(request, response);
    return;
}
String token = header.substring(7);
String email = jwtService.extractEmail(token);

if (email != null && SecurityContextHolder.getContext().getAuthentication() == null) {
    UserDetails user = userDetailsService.loadUserByUsername(email);
    if (jwtService.isValid(token, user)) {
        var auth = new UsernamePasswordAuthenticationToken(
            user, null, user.getAuthorities());
        SecurityContextHolder.getContext().setAuthentication(auth);
    }
}
filterChain.doFilter(request, response);

Qué hace cada parte

  • Lee el header Authorization. Si no viene o no empieza con Bearer , deja pasar sin autenticar.
  • substring(7): corta el prefijo Bearer y se queda con el token puro.
  • Extrae el email del token (verifica firma de paso).
  • Carga el usuario desde BD y valida que el token le corresponde y no expiró.
  • Crea el objeto Authentication y lo guarda en SecurityContextHolder — esto deja al usuario "logueado" para este request.
  • Sigue la cadena: el siguiente filtro decide si el endpoint requiere autenticación.

Autorización por endpoints

Dos estilos, ambos válidos. Se pueden combinar.

1. Centralizado en SecurityConfig

.authorizeHttpRequests(auth -> auth
    .requestMatchers("/api/auth/**").permitAll()
    .requestMatchers("/api/admin/**").hasRole("ADMIN")
    .requestMatchers(HttpMethod.POST, "/api/bill-payments")
        .hasAnyRole("CUSTOMER","ADMIN")
    .anyRequest().authenticated())

2. Anotaciones por método

@PreAuthorize("hasRole('ADMIN')")
@DeleteMapping("/{id}")
public void delete(@PathVariable Long id) { ... }

Cuándo usar cada uno

  • Centralizado: cuando la regla es por URL completa (todos los /api/admin/**). Mantiene una sola vista de la seguridad.
  • Anotación: cuando depende de la lógica del método (ej: "sólo el dueño del recurso o un admin"). Necesita @EnableMethodSecurity.
  • hasRole("ADMIN") internamente busca la autoridad ROLE_ADMIN — por eso el UserDetailsService agrega el prefijo.

Logout: el problema con JWT

Un JWT firmado es válido hasta que exp pasa, aunque el usuario haya cerrado sesión. El servidor no guarda registro de los tokens emitidos.

Imagina este escenario:

  1. Ana se loguea desde un cibercafé. Recibe un token con exp en 60 minutos.
  2. Ana hace click en "Cerrar sesión" y se va.
  3. Otra persona toma la PC. Si ese token fue robado del localStorage, aún funciona 59 minutos más.

Necesitamos una forma de invalidar el token antes de que expire naturalmente.

Estrategia elegida: Refresh Tokens

Es el estándar de la industria (OAuth2, Auth0, AWS Cognito). Dos tokens trabajando en equipo:

1

Access Token (JWT corto)

Vive 15 minutos. Viaja en cada request en Authorization: Bearer .... Stateless: el servidor no lo guarda. Si se roba, sólo es útil 15 min.

2

Refresh Token (UUID en BD)

Vive 7 días. Se guarda en la tabla refresh_tokens. Sirve para pedir un nuevo access token sin reingresar credenciales. Se revoca en logout.

3

Logout

Marca el refresh token como revoked = true. El access expira solo en menos de 15 min. Sin blacklist, sin Redis.

Flujo completo con refresh tokens

1 POST /api/auth/login → { accessToken (15min), refreshToken (7d) }
2 Cliente llama endpoints con Authorization: Bearer <accessToken>
3 A los 15 min el access expira → 401
4 Cliente llama POST /api/auth/refresh con el refresh token
5 Backend valida en BD que el refresh existe, no expiró y no está revocado
6 Backend emite nuevo access token (refresh sigue igual)
7 POST /api/auth/logout con el refresh → marca revoked = true
8 Cliente borra ambos tokens de su almacenamiento

Implementación: entidad y servicio

@Entity @Table(name = "refresh_tokens")
public class RefreshToken {
  @Id @GeneratedValue Long id;
  @Column(unique = true) String token;     // UUID
  @ManyToOne User user;
  LocalDateTime expiresAt;
  boolean revoked;
}

@Service
public class RefreshTokenService {
  public RefreshToken create(User user) {
    RefreshToken rt = new RefreshToken();
    rt.setToken(UUID.randomUUID().toString());
    rt.setUser(user);
    rt.setExpiresAt(LocalDateTime.now().plusDays(7));
    rt.setRevoked(false);
    return repo.save(rt);
  }

  public RefreshToken validate(String token) {
    RefreshToken rt = repo.findByToken(token)
        .orElseThrow(() -> new InvalidTokenException());
    if (rt.isRevoked() || rt.getExpiresAt().isBefore(now()))
        throw new InvalidTokenException();
    return rt;
  }

  public void revoke(String token) {
    repo.findByToken(token).ifPresent(rt -> {
      rt.setRevoked(true);
      repo.save(rt);
    });
  }
}

Qué hace cada parte

  • RefreshToken: entidad JPA con UUID único, dueño, expiración y flag revoked.
  • create(): se llama al hacer login. Emite un UUID aleatorio con 7 días de vida.
  • validate(): tres condiciones — existe en BD, no expiró, no fue revocado. Si falla, 401.
  • revoke(): el endpoint logout lo invoca. Marca revoked = true en BD.
  • Para "logout en todos los dispositivos": repo.revokeAllByUserId(userId).

Implementación: endpoints

// AuthService
public AuthResponse login(LoginRequest req) {
  authManager.authenticate(
    new UsernamePasswordAuthenticationToken(
      req.email(), req.password()));
  User user = userRepo.findByEmail(req.email()).orElseThrow();
  String access = jwtService.generateToken(user);
  RefreshToken refresh = refreshTokenService.create(user);
  return new AuthResponse(access, refresh.getToken());
}

public AuthResponse refresh(String refreshToken) {
  RefreshToken rt = refreshTokenService.validate(refreshToken);
  String newAccess = jwtService.generateToken(rt.getUser());
  return new AuthResponse(newAccess, refreshToken);
}

public void logout(String refreshToken) {
  refreshTokenService.revoke(refreshToken);
}

// AuthController
@PostMapping("/login")    public AuthResponse login(...)    { ... }
@PostMapping("/refresh")  public AuthResponse refresh(...)  { ... }
@PostMapping("/logout")   public void logout(...)            { ... }

Qué hace cada parte

  • login: emite ambos tokens. El access dura 15 min, el refresh 7 días.
  • refresh: intercambia un refresh válido por un nuevo access. El refresh no se renueva (rotación opcional).
  • logout: revoca el refresh. El access seguirá funcionando hasta su exp, pero ya no se puede renovar.
  • Tres endpoints, todos en /api/auth/** (públicos, no requieren JWT válido para llamarlos).

Configuración: duración de los tokens

¿De dónde sale el "15 min" y "7 días"? De variables de entorno en milisegundos.

En el .env

JWT_EXPIRATION_MS=900000
JWT_REFRESH_EXPIRATION_MS=604800000

Cálculo: días × 24 × 60 × 60 × 1000

  • 900.000 ms = 15 min (access)
  • 604.800.000 ms = 7 días (refresh)

El env se inyecta vía @Value en RefreshTokenService. Cambiás el número, reiniciás la app — sin recompilar.

¿Cuándo se invoca /refresh desde el frontend?

Confunde a todos: los 7 días son la vida del refresh, NO la frecuencia de llamada. /refresh se invoca cada ~15 min mientras el usuario use la app.

// Interceptor Axios: si recibe 401, hace refresh y reintenta
axios.interceptors.response.use(
  res => res,
  async error => {
    const original = error.config;
    if (error.response?.status === 401 && !original._retry) {
      original._retry = true;
      try {
        const { data } = await axios.post('/api/auth/refresh', {
          refreshToken: localStorage.getItem('refresh')
        });
        // Guardar los DOS nuevos (rotation)
        localStorage.setItem('jwt', data.accessToken);
        localStorage.setItem('refresh', data.refreshToken);
        original.headers.Authorization = `Bearer ${data.accessToken}`;
        return axios(original);
      } catch {
        localStorage.clear();
        window.location.href = '/login';
      }
    }
    return Promise.reject(error);
  }
);

El flujo, paso a paso

  • Usuario hace login → guarda ambos tokens.
  • Cada request lleva Authorization: Bearer <accessToken>.
  • A los 15 min, el access expira → API responde 401.
  • El interceptor atrapa el 401 y llama /refresh con el refresh token.
  • Recibe access nuevo + refresh nuevo (por rotation), los guarda y reintenta el request original.
  • Si el refresh también falla (logout o pasaron 7 días), redirige a /login.

Los 7 días son el techo de inactividad: si abrís la app al día 8 sin haber usado nada, te pide login. Si la usás cada día, los tokens se renuevan transparente.

Buenas prácticas

  • BCrypt para passwords. Jamás texto plano ni MD5/SHA1.
  • Secret JWT en variable de entorno (JWT_SECRET), nunca en el código.
  • Expiración corta (15-60 min) + refresh token separado para sesiones largas.
  • HTTPS siempre en producción: el token viaja en cada request.
  • HS256 con secret ≥ 256 bits, o RS256 con par de llaves.
  • No metas datos sensibles en el payload (es público).
  • Endpoints públicos explícitos: permitAll() sólo donde corresponde.
  • SessionCreationPolicy.STATELESS en APIs REST.
  • Implementa logout real con refresh tokens (revocar en BD).

Errores comunes

  • 401 sin endpoints públicos: olvidar permitAll() en /api/auth/** y Swagger.
  • 403 después de loguear: el filtro JWT no se ejecuta antes del filtro de auth.
  • Secret hardcoded en SecurityConfig commiteado al repo.
  • Tokens sin expiración: si se roban, son válidos para siempre.
  • Token en cookie no HttpOnly: vulnerable a XSS.
  • Olvidar @EnableMethodSecurity y luego sorprenderse de que @PreAuthorize no hace nada.
  • "Implementar logout" borrando el token sólo del cliente: el token sigue siendo válido en el servidor.
